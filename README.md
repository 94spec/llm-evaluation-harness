# LLM Evaluation Harness

[![tests](https://github.com/94spec/llm-evaluation-harness/actions/workflows/tests.yml/badge.svg)](https://github.com/94spec/llm-evaluation-harness/actions/workflows/tests.yml)
[![release](https://img.shields.io/github/v/release/94spec/llm-evaluation-harness)](https://github.com/94spec/llm-evaluation-harness/releases/latest)

Dependency-free Python harness for evaluating structured LLM outputs in
conversation-intelligence pipelines. It covers four task families:

1. weighted QA scorecards;
2. deal summaries;
3. semantic analytics;
4. violations and safety flags.

**What this repository is.** A clean-room reference implementation, written from scratch to
document how I evaluate LLM systems in production. It carries no employer code, data, prompts
or configuration: every fixture here is synthetic and generated by the tool itself. The point
is that the controls — golden sets, task-appropriate metrics, error taxonomy, release gates —
can be inspected and rerun by anyone, without an API key and without a single production record.

## Why this exists

An LLM system is not production-ready because a few outputs look plausible. A release needs:

- a versioned, human-adjudicated golden set;
- task-appropriate metrics rather than one blended “accuracy” number;
- uncertainty estimates;
- a stable error taxonomy;
- regression gates for quality, schema compliance, latency, and cost;
- traceability from model, prompt, schema, and pricing snapshot to every report.

This harness makes those controls reproducible without requiring an external model API.

## Recommended golden-set design

Use four task-specific panels of **500 deals each**. The panels may overlap, but each family has
its own inclusion criteria and annotation guide. A single deal can therefore yield up to four
evaluation records. Keep a permanently frozen test split and a separate development set.

Suggested strata:

- call-chain length: one / two / three or more calls;
- total conversation duration: short / medium / long;
- outcome: won / lost / follow-up / undecided;
- traffic readiness: cold / warm / hot / insufficient data;
- transcript quality: clean / noisy / speaker ambiguity;
- edge cases: short technical contacts, voicemail, repeated calls, missing evidence;
- calendar period and business unit, with no personally identifiable data in the public set.

See [METHODOLOGY.md](METHODOLOGY.md) for annotation, adjudication, agreement, bootstrap, and
release-gate guidance.

## Metrics

| Family | Primary metrics | Important safeguards |
|---|---|---|
| QA scorecard | criterion accuracy, macro-F1, Cohen’s κ, weighted-score MAE | score recomputed from criterion labels; model score consistency |
| Deal summary | schema validity, outcome accuracy/κ, content-unit precision/recall/F1, exact slots | hallucinated and omitted facts tracked separately |
| Semantic analytics | micro/macro-F1, exact-set match, Jaccard, readiness accuracy/κ | metrics by semantic dimension |
| Violations | recall/F1, critical recall, false-negative rate, κ | critical misses are release-blocking |

Every scalar quality metric can receive a deal-level percentile-bootstrap 95% confidence
interval. Human annotation reliability is reported separately using Cohen’s kappa for two
raters and Krippendorff’s alpha (nominal) for two or more raters.

## Quick start

No third-party runtime dependencies are required.

```bash
# The package lives in src/, so tests and the CLI need it on the module path.
PYTHONPATH=src python -m unittest discover -s tests -v

# Generate four synthetic panels, 500 deals per task family.
PYTHONPATH=src python -m conv_eval generate \
  --out fixtures/generated \
  --deals-per-family 500 \
  --seed 20260728

# Evaluate one synthetic run and build JSON + Markdown reports.
PYTHONPATH=src python -m conv_eval evaluate \
  --gold fixtures/generated/golden.jsonl \
  --predictions fixtures/generated/predictions.candidate.jsonl \
  --manifest fixtures/generated/run.candidate.json \
  --json-out reports/generated/candidate.json \
  --markdown-out reports/generated/candidate.md \
  --bootstrap 1000 \
  --seed 20260728

# Compare a candidate with a baseline and enforce release gates.
PYTHONPATH=src python -m conv_eval gate \
  --baseline reports/generated/baseline.json \
  --candidate reports/generated/candidate.json \
  --config configs/regression_gates.demo.json \
  --out reports/generated/gate.json
```

On Windows PowerShell, set the module path first:

```powershell
$env:PYTHONPATH = "src"
python -m conv_eval generate --out fixtures/generated --deals-per-family 500
```

Regression thresholds are configured per deployment and versioned alongside the rubric,
dataset, prompt, schema, and model manifest.

## Commands

- `generate`: creates deterministic synthetic golden panels, two prediction runs, and run
  manifests. It never calls an LLM.
- `evaluate`: validates outputs, computes task metrics, confidence intervals, operational
  metrics, annotation agreement, and a typed error ledger.
- `compare`: creates a compact provider/model quality-cost-latency comparison from reports.
- `gate`: applies absolute and baseline-relative release rules; exits with code `2` on failure.

Use `python -m conv_eval <command> --help` for options.

## Run manifest

Each evaluation is bound to a manifest containing:

- dataset and run identifiers;
- provider and model identifier;
- prompt and output-schema versions;
- code revision;
- generation parameters;
- pricing snapshot and its effective date.

Latency and token counts belong to individual prediction records. Estimated cost is calculated
from the immutable pricing snapshot in the manifest; it is never silently inferred from a
current vendor price.

## Agreement metric contract

Agreement can be reported at two levels, and mixing them up is the most common way to
overstate a result. Both are stated explicitly in every report:

```text
decision-level agreement = matching model-vs-gold decision states / evaluated decision states
deal-level agreement     = deals where every evaluated decision matches / evaluated deals
```

The deal count describes the evaluation sample; the decision-state count is the finer
denominator. Deal-level agreement is the stricter of the two and is the number I quote in
portfolio material — a deal counts as agreeing only when the model matched the adjudicated
verdict on that deal.

Reports pair agreement with a deal-cluster bootstrap 95% confidence interval,
critical-violation recall, weighted-score MAE, schema validity, and the complete run manifest.
An average agreement figure alone is never a release criterion: critical-violation recall is
gated separately, because that is exactly the class of miss an average hides.
